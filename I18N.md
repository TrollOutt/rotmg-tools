# Internationalisation de Realm Tools

Realm Tools utilise une couche i18n légère, sans dépendance, adaptée à son architecture JavaScript statique. Les règles métier sont définies dans [CHARTE_LOCALISATION_ROTMG.md](CHARTE_LOCALISATION_ROTMG.md).

## Architecture

- `web/i18n.js` : détection, fallback, persistance, sélecteur, traduction du DOM et formatage `Intl`.
- `web/locales/<locale>/common.json` : catalogues à clés sémantiques.
- `web/locales.js` : bundle navigateur généré par `npm run i18n:compile`.
- `tools/check-i18n.js` : égalité des clés, chaînes vides et placeholders.
- `tools/translate-static-i18n.js` : aide de migration pour les seuls textes UI littéraux des fichiers HTML ; elle ne lit jamais les données ROTMG.
- `tests/i18n.test.js` : détection, persistance, fallback, nombres, recherche et invariants ROTMG.

## Choix de la langue

Le sélecteur vit dans la barre d’actions fixe en haut à droite (`#corner`), juste après **Feedback**, et il est construit par `web/i18n.js` : aucun balisage à maintenir, une langue ajoutée à `LOCALES` est une langue dans le menu. Il reprend les `corner-button` et le panneau du formulaire de retour, au clavier comme à la souris (flèches, `Début`/`Fin`, `Échap`, fermeture au clic extérieur).

Ordre de résolution, appliqué une seule fois dans `resolve()` :

1. préférence enregistrée dans `localStorage` sous `realm-tools/locale`, si ce n’est pas `auto` ;
2. paramètre d’URL `?lang=` — il affiche une page dans une langue sans jamais écrire la préférence ;
3. langues du navigateur (`navigator.languages`, puis `navigator.language`) ;
4. `en`.

La clé `realm-tools/locale` contient donc **la réponse** — `auto` ou un code de langue — et non la langue résolue. Une valeur écrite par une version précédente reste valide : c’est un code de langue, donc un choix explicite. Rien d’enregistré équivaut à `auto`, ce qui fait qu’une première visite arrive dans la langue du lecteur sans que personne n’ait eu à la demander.

Aucune géolocalisation n’est interrogée : le site est une page statique sur GitHub Pages, il n’existe donc aucun en-tête d’hébergeur à lire, et demander à un tiers où se trouve un visiteur pour deviner ce qu’il lit enverrait son adresse ailleurs pour répondre à une question que son navigateur a déjà mieux résolue.

`match()` ramène une étiquette de langue à un catalogue : correspondance exacte, puis langue de base (`fr-CA` → `fr`, `en-AU` → `en`). Deux familles sont nommées explicitement. Le portugais, parce que les deux catalogues sont deux langues en pratique : `pt-BR` pour le Brésil, `pt` seul et toute autre région pour le Portugal — un navigateur brésilien annonce toujours `pt-BR`. Le chinois, parce que la séparation est scripturale : `zh`, `zh-Hans`, `zh-CN` et `zh-SG` donnent `zh-CN` ; le traditionnel (`zh-TW`, `zh-Hant`, `zh-HK`, `zh-MO`) n’est volontairement pas replié dessus et passe à la préférence suivante.

Le fallback de toute clé absente est `en`.

Chaque langue est accompagnée d’un drapeau (`FLAGS`), et `auto` d’un globe. Le drapeau est décoratif : il est toujours accompagné du nom natif de la langue, il porte `aria-hidden`, et le bouton annonce en toutes lettres la langue et le mode (`Langue : Automatique (Français)`). Windows ne dispose d’aucun glyphe de drapeau : Chrome y affiche le code pays à deux lettres à la place, ce qui reste lisible et reste accompagné du nom.

## Ajouter une langue

1. Ajouter le code, son nom natif et son drapeau dans `LOCALES`/`NAMES`/`FLAGS` de `web/i18n.js`, puis le code dans `tools/build-i18n.js` et `tools/check-i18n.js`.
2. Copier `web/locales/en/common.json` vers `web/locales/<locale>/common.json` et traduire toutes les valeurs.
3. Exécuter `npm run i18n:check` puis `npm run i18n:compile`.

## Ajouter une clé

Ajouter la même clé sémantique et les mêmes placeholders dans chaque `common.json`. Utiliser `RealmI18n.t('clé', { variable })` dans le JavaScript ou `data-i18n="clé"` dans le HTML. Les chaînes anglaises historiques explicitement présentes dans le catalogue sont également reconnues lors du rendu dynamique.

Les nombres et dates doivent passer par `RealmI18n.number(value, options)` et `RealmI18n.date(value, options)`. Les valeurs internes restent numériques.

## Ajouter une entité ROTMG

Conserver son nom anglais canonique dans les données et dans l’affichage principal. Ne jamais créer une identité traduite. Les alias locaux éventuels appartiennent uniquement à l’index de recherche. `RealmI18n.canonicalSearch` transforme les concepts localisés (par exemple `dextérité`) vers leur terme de recherche canonique sans altérer `DEX` ni `Potion of Dexterity`.

Pour décider si un terme doit être traduit : identifier son type, puis appliquer `CHARTE_LOCALISATION_ROTMG.md`. En cas d’ambiguïté, garder l’anglais et documenter le cas.

## Vérifier localement

```text
npm run i18n:check
npm run i18n:compile
npm test
npm run build
```

Lancer ensuite `npm run dev`, changer la langue avec le sélecteur placé à côté de Feedback et vérifier les vues principales à largeur bureau et mobile, ainsi que le retour à `Automatique`.

`npm run i18n:check` signale aussi, sans échouer, les textes de la page d’accueil (`MODULES` dans `web/app.js`) qui ne sont pas encore au catalogue : ils sont construits en JavaScript, donc invisibles pour l’analyse du balisage.

Les libellés essentiels ont été révisés manuellement. Les longues phrases ajoutées par l’aide de migration sont signalées comme traductions assistées et doivent faire l’objet d’une relecture par des locuteurs natifs avant une publication considérée comme définitive, notamment pour distinguer le portugais brésilien du portugais européen.
