# Baseline before the modernisation — 2026-10-14

Step 0 of the Vite / TypeScript / Web Workers / (maybe) Rust-WASM plan. Nothing
was migrated. This file records what the repository measured like *before* any
of that, so later steps can be compared with it and nobody has to remember.

Re-run the numbers with the commands in "How to reproduce". Milliseconds are
indicative of one machine on one day; counts and sizes are exact.

## What was measured, and on what

- **Snapshot.** A copy of the working tree at HEAD `f20d516` **plus two
  uncommitted files** that were modified at the time (`web/style.css`,
  `web/whats-new.js`). It is not HEAD alone. The copy had no `.git` of its own
  and was given a minimal index holding exactly the tracked files, because
  `tools/provenance.js` asks git which files are tracked and otherwise checks
  untracked scratch such as `data/Database/` and fails for the wrong reason.
- **Why a copy.** `npm run build` and `npm test` rewrite generated files
  (`web/locales.js`, `docs/`); they were run in the copy so nobody's
  uncommitted work was touched.
- **Machine.** Windows 11, 16 hardware threads (laptop-class AMD Ryzen 7),
  Node v20.17.0, npm 11.3.0, Python 3.12, Chrome (current at the time) for the browser runs.
- **Not the published site.** Browser numbers come from a static file server on
  loopback with no HTTP cache headers, not from GitHub Pages.

### Theory Crafting optimiser — Node timing, not browser timing

Measured with `tools/bench-theory.js` (1 warm-up + 7 timed searches per case).
The search has no randomness, so candidate counts are exact and identical on
every run and every machine; times are not.

| Search | Candidates looked at | median ms |
|---|---|---|
| Wizard / dps | 4 858 | 345–407 |
| Archer / dps | 3 445 | 210–294 |
| Warrior / stat:hp | 4 497 | 239–321 |

The ranges are the spread between independent runs on the same machine within
one afternoon (a first run, a second one with the committed script and a third
under `--check`): about ±15–20 %. Treat any single run as one sample.

Full catalogue, 19 classes × 10 goals = 190 searches, one timed search each:
719 297 candidates in total, at most 6 304 for one search (Necromancer / kill,
the slowest). Per-search time: median 215–250 ms, p95 342–428 ms, slowest single
search 525–659 ms, across two full runs.

**What this is not.** In the browser the same search runs as a generator that
hands control back to the event loop every ~12 ms
(`runOptimiserStepsAsync` in `web/theorycraft.js`), so the page keeps
answering while it works and its total time is longer than the Node figure.
No browser run of a full optimisation, and no count of how many searches one UI
action starts, has been measured yet. These numbers say nothing about frames,
input latency, parsing or painting, and by themselves they do not justify Rust
or WASM.

### The site in a browser (loopback, uncached, no GitHub Pages)

- Served page: DOMContentLoaded 775 ms, load 1051 ms, 21 resources, ~18 MB
  decoded.
- First opening of each page, main-thread blocking as `BENCH.site()` measures
  it: enchant 21 ms, theory 4 ms, index 6 ms, fame 23 ms, news 6 ms. JS heap
  114 MB afterwards. These are blocking times for the call that switches page,
  not time to usable content, and they are single samples.
- `BENCH.site()`'s frame part could not run: the browser pane used was hidden,
  where `requestAnimationFrame` does not fire. It needs a visible browser.
- `assets/index/realmeye-enrichment.json` (11.9 MB) was requested **three
  times** in one session, from three independent fetch sites
  (`web/fiches-c.js`, `web/index-page.js`, `web/theorycraft.js`). HTTP caching
  on Pages probably spares the transfer; whether it spares the three parses and
  the memory was not measured.

### The standalone file opened from disk (`file://`)

Run in headless Chrome against `docs/Realm-Tools.html`, with `fetch` calls to
other origins replaced by rejections (the real network was not cut for
non-`fetch` loads), and a small diagnostic script appended to the copy.

- It loads. The five pages (enchant, theory, index, fame, news) activate and
  render content. The bundle holds 15 sources. The Skin Viewer is absent and
  says so, pointing to the website.
- `assets/ui/backgrounds/facets.webp` is referenced and not embedded; it fails
  to load beside the single file.
- The Atlas is not in the file by decision (24 MB). By reading `pointAtAtlas()`
  it degrades through a failing `HEAD` request; that was read, not observed.
- `Uncaught RangeError: Invalid string length` was seen in one of three runs and
  has not been reproduced or located.

Not validated: that each tool *works* offline beyond showing content, or any
behaviour with the network really cut.

## Findings

1. **The visitor counter ran everywhere.** `web/app.js` and
   `tools/atlas-viewer.html` asked the public Abacus service for the total, the
   day and the minute from any origin, so every local run added to the real
   tally. The measurements above did so too before the calls were stubbed.
   Fixed on branch `task/visit-counter-guard`.
2. **`realmeye-enrichment.json` is loaded three times** (see above).
3. **`facets.webp` is not embedded** in the standalone file.
4. **An unexplained `RangeError`** in the standalone file, one run in three.
5. **The standalone contract is weak.** `tests/standalone.test.js` allows a
   missing relative asset and proves nothing about offline use.
6. **Two network dependencies besides the counter:** Google Fonts
   (`Jersey 10`) is requested by the page.

## Decisions taken with this baseline

- The 24 MB Atlas is **not** inlined into `Realm-Tools.html`. Features that are
  not available offline (Atlas, Skin Viewer) are to be documented as such. An
  offline ZIP that includes the Atlas is a possible later option, not now.
- Vite, TypeScript, a lockfile and `npm ci` in the GitHub Actions workflow are
  accepted, but are installed only by the step that needs them. GitHub Pages
  and both distributions (web and standalone) are to be preserved.
- No migration step starts before the three follow-ups below.

## Budgets proposed (to ratify once noise is measured)

- Keep the absolute `index.html` limit as it is; track raw bytes and gzip
  separately for both HTML files. Do not reset the reference at each step.
- A change expected to bring no functional or performance benefit should leave
  sizes stable, and any growth is explained.
- Opening-time budgets need a measured p95 and a measured noise level first.
  Provisional trigger for investigation: a reproducible rise above
  `max(5 ms, 20 % of baseline)`.
- Workers: at least 30 % less main-thread blocking on the targeted scenarios,
  and at most 10 % more total time. Rust/WASM only if a realistic action stays
  at 250 ms or more at p95 after Workers, the kernel is at least half of that
  time, and measured gains are at least 3× on the kernel and 2× on the action
  with at least 100 ms saved. These are proposals, not observed performance.

## Next, in order

1. Diagnose the offline `RangeError`.
2. Embed or drop the `facets.webp` reference in the standalone file, then
   tighten `tests/standalone.test.js` with an explicit list of allowed external
   files (the Atlas).
3. Analyse and, if justified, share the three loads of
   `realmeye-enrichment.json`.
4. Measure in a visible browser: the whole `BENCH.site()`, a p95 of page
   opening, and the real cost and count of an optimisation started from the UI.

## How to reproduce

```
npm run build
npm test
npm run bench:theory                       # nine searches, 1 warm-up + 7 timed
npm run bench:theory -- --full             # 19 classes x 10 goals, once each
npm run bench:theory -- --json base.json   # keep the answers
npm run bench:theory -- --check base.json  # prove a change left them unchanged
```

`--check` compares candidates looked at and a digest of the score and the
build, never milliseconds. For the browser: serve `web/` over HTTP, open it in a
**visible** browser, load `tools/bench.js` as described at its top, and
`await BENCH.site()`. To open the standalone file offline, use a copy whose
requests to other origins are blocked, so the real counter is not touched.

Raw build and test logs were not committed: they are long and carry nothing the
tables above do not.
